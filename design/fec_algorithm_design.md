## 2. 修订后的结论

本模块不需要理解采样率、声道、编码格式或播放策略。DSP 在发送原始数据包前调用 FEC 编码接口，接收端把收到的 FEC 帧交给解码接口，解码器向 DSP 返回与发送端输入逐字节一致的原始数据包。

在“包内容不透明、部署于资源受限嵌入式设备、需要低且确定的计算开销”的新边界下，建议调整首版实现优先级：

1. **首版优先实现一维 XOR + 交织。**它只有 XOR、计数和位图操作，不需要有限域乘法、矩阵求逆或动态内存；适合中低端 MCU，也直接针对 2.4 GHz 常见的连续突发丢包。
2. **保留系统型缩短 RS 作为增强 profile。**当丢包不是连续突发，而是同一交织列出现两个以上离散丢包，或系统无法接受较长交织窗口时，短块 RS 更稳健。
3. **通过统一接口隔离算法。**DSP 不应知道当前使用 XOR 还是 RS；算法、参数和帧格式版本由 `fec_profile` 决定。
4. **最终默认参数不能只看平均丢包率。**必须同时测量连续丢包长度、同列多丢包概率、最大可等待窗口、RAM 和目标 MCU 的 cycles/byte。

这不是认定 XOR 在纠错能力上强于 RS。XOR+交织用更长的时间跨度和缓存换取极低 CPU，并将连续丢包分散到多个独立单校验组；RS 用更高计算量换取“任意位置多丢包”的确定性恢复能力。

## 3. 模块职责与边界

### 3.1 模块负责

- 接收任意二进制上层数据包，不解析其业务内容。
- 给源包添加 FEC 传输头，生成系统型源帧。
- 按配置生成 XOR 交织修复帧；后续可生成 RS 修复帧。
- 接收源帧和修复帧，识别丢包、重复包、乱序包和无效包。
- 在恢复条件满足时重建原始数据包，并恢复原始长度。
- 在窗口关闭后输出成功、不可恢复、超时或参数错误状态。
- 提供编码、解码、丢包和性能统计。

### 3.2 模块不负责

- 不解析或处理音频内容。
- 不决定 DSP 何时播放数据。
- 不完成设备间时钟同步、重采样或 PLC。
- 不执行 RF 发包调度、重传、跳频或信道选择。
- 不替代底层 PHY/链路 CRC；校验失败的无线帧必须在进入 FEC 解码器前丢弃。

### 3.3 上下游数据流

```text
发送端：DSP packet -> FEC encoder -> FEC source/repair frames -> RF transport

接收端：RF valid frames -> FEC decoder -> original DSP packets -> DSP
```

FEC 模块只保证成功输出的数据与发送端输入逐字节相同。包的业务时限由调用者通过配置或过期接口告诉 FEC，FEC 不推测业务含义。

## 4. 为什么采用包擦除 FEC

底层无线包经过 CRC 后，接收端面对的是两种状态：包正确到达，或已知序号的包没有到达。这属于包擦除信道。

本模块应使用 XOR、RS 等包擦除码。BCH、卷积码、Turbo、PHY LDPC 和 Polar 等算法主要处理包内部未知位置的比特错误，往往依赖软判决并与调制解调器紧密结合，不属于本模块范围。

接收顺序必须是：

```text
RF -> PHY/链路层纠错 -> CRC/完整性检查 -> 无效包转为擦除
   -> FEC 包级解码 -> 原始 DSP 包
```

错误帧如果未被识别就参与 XOR 或 RS 运算，可能污染恢复结果，因此“错误检测”是 FEC 正确工作的前置条件。

## 5. 候选算法比较

| 算法 | 主要能力 | 编码成本 | 解码成本 | 缓存/窗口 | 适用判断 |
| --- | --- | --- | --- | --- | --- |
| 重复发送 | 以副本抵抗丢包 | 拷贝 | 拷贝/选择 | 很小 | 100% 以上开销，仅调试或紧急模式 |
| 单组 XOR | 每组恢复任意 1 个丢包 | 每源包一次 XOR | 一次 XOR 归约 | 小 | 算力最低，但连续两包常导致失败 |
| **XOR + 交织** | 将突发丢包分散到多个 XOR 组 | 每源包一次 XOR | 每组一次 XOR 归约 | 随交织深度增加 | **首版推荐** |
| 系统型 RS | 每块恢复任意 r=n-k 个丢包 | r 次 GF 乘加 | 小矩阵求解 + GF 乘加 | 短块可控 | 增强 profile |
| 滑动窗口 RLC | 跨窗口连续产生线性修复包 | 随窗口和密度增加 | 持续维护线性方程组 | 状态较复杂 | 当前不作为首版 |
| RaptorQ | 大块可生成大量修复符号 | 中到高 | 中到高 | 偏大 | 更适合对象/文件分发 |
| 包级 LDPC | 大块下效率较好 | 中 | 迭代解码 | 偏大 | 当前小型实时模块不优先 |

## 6. XOR + 一维交织方案

### 6.1 参数定义

将连续的 `D × L` 个源包按 D 行、L 列排列：

- `D`：每个 XOR 校验组中的源包数，即矩阵行数；决定冗余比例。
- `L`：并行交织列数，即交织深度；决定可分散的连续突发长度。
- 每一列生成 1 个 XOR 修复包，共生成 L 个修复包。
- 总源包数为 `D × L`，总修复包数为 L。
- FEC 冗余开销为 `L / (D × L) = 1 / D`。

源包序号在块内记为 `q=0..D×L-1`：

```text
row = floor(q / L)
col = q mod L
```

第 c 列修复符号为：

```text
P[c] = S[c] XOR S[L+c] XOR S[2L+c] ... XOR S[(D-1)L+c]
```

### 6.2 D=4、L=4 示例

```text
               col0      col1      col2      col3
row0           S0        S1        S2        S3
row1           S4        S5        S6        S7
row2           S8        S9        S10       S11
row3           S12       S13       S14       S15
repair         P0        P1        P2        P3
```

其中：

```text
P0 = S0 XOR S4 XOR S8  XOR S12
P1 = S1 XOR S5 XOR S9  XOR S13
P2 = S2 XOR S6 XOR S10 XOR S14
P3 = S3 XOR S7 XOR S11 XOR S15
```

该配置保护 16 个源包并发送 4 个修复包，冗余开销为 25%。如果连续丢失的传输符号数量不超过 4，且发送顺序保证这些符号落入不同列，那么每列最多只有一个擦除，可分别恢复。

### 6.3 恢复规则

对每一列独立处理：

- 0 个源包丢失：不需要解码；源包可直接输出。
- 1 个源包丢失且修复包到达：用修复包 XOR 其余 D-1 个源包，恢复缺失源包。
- 2 个或更多源包丢失：该列不可恢复。
- 1 个源包和该列修复包同时丢失：该列不可恢复。
- 只有修复包丢失、所有源包都到达：不影响原始数据输出。

交织提高的是对特定丢包形态的能力，不改变每列只能恢复一个源包的本质。例如 S0 和 S4 是非连续丢包，但它们位于同一列，即使其他列无丢包也无法恢复。

### 6.4 突发保护成立的发送约束

建议空口逻辑顺序保持为：

```text
S0, S1, ... S(D×L-1), P0, P1, ... P(L-1)
```

源包和修复包都按 `col=0..L-1` 的周期顺序排列，使长度不超过 L 的单次连续空口擦除不会在同一块内重复命中同一列。若 RF 层自行重排、复制或按优先级插入帧，必须保证这种列间隔性质，或者重新计算实际突发保护能力。

不建议在最后一行每收到一个源包后立即相邻发送对应列的修复包。例如紧邻发送 `S12,P0` 会让一次短突发同时丢掉源包和它的恢复依据。

如果源流和修复流走不同队列、时隙或频点，则必须基于实际发送时间线验证，而不能仅根据逻辑包序号宣称可恢复 L 个连续丢包。

### 6.5 变长包处理

XOR 要求同一列的保护符号在逻辑上等长。FEC 不修改 DSP 包内容，而是构造如下“受保护符号”：

```text
[original_length | source_integrity | original_packet | implicit_zero_padding]
```

- `original_length` 用于恢复后去掉补零。
- `source_integrity` 用于确认恢复结果没有被错误输入污染。
- `original_packet` 是 DSP 传入的完整不透明字节串。
- `implicit_zero_padding` 在 XOR 运算时把逻辑符号补到 profile 固定的 `symbol_size`。

零填充只存在于计算语义中，不应真的随正常 SOURCE 帧发送。SOURCE 帧只发送长度、完整性字段和实际 DSP 数据；编码器与解码器的累加缓冲区预先清零，未传输的尾部自然按零处理。REPAIR 帧需要携带完整的有效奇偶校验范围。

最大 DSP 包长度必须满足：

```text
max_dsp_packet <= RF_MTU - FEC_outer_header - protected_metadata
```

如果允许每块动态选择 `symbol_size`，可减少小包的无效 XOR 和修复包长度，但会增加协议状态和错误分支。首版建议每个 profile 固定最大逻辑符号长度，SOURCE 帧仍按实际长度发送，优先兼顾确定性和源包空口效率。

## 7. XOR + 交织的嵌入式性能设计

### 7.1 编码端

编码器维护 L 个修复累加缓冲区。每个源包只进入一个列累加器：

```text
parity[col] ^= protected_symbol
```

每处理一个源包，主要计算量约为 `symbol_size` 字节的 XOR，与 D 无关。源包可以系统型输出，不需要等待整个块。

当完成 D 行后，输出 L 个修复包，然后复用累加缓冲区处理下一块。

### 7.2 解码端

如果允许收到的正常源包立即交给 DSP，解码端不必保存全部 `D×L` 个源包。每列只需维护：

- 一个 XOR 累加缓冲区；
- D 位源包到达位图；
- 修复包到达标志；
- 块号、列号、长度和超时状态。

收到源包时立即输出给 DSP，同时把其受保护符号 XOR 到列累加器；收到修复包后也加入对应恢复状态。块关闭时，如果恰有一个源包缺失，就可恢复。

如果 DSP 强制要求严格按序回调，FEC 或其上层还需要重排缓存，这会把 RAM 从约 `L×symbol_size` 提升到最坏约 `D×L×symbol_size`。建议 FEC 输出携带 `source_seq`，允许 DSP 或独立重排层决定是否等待，避免把业务排序策略固化进算法核心。

### 7.3 RAM 估算

不考虑结构体、对齐和输出队列时，编码或流式解码核心累加区约为：

```text
RAM_accumulator ≈ L × protected_symbol_size
```

例如 D=4、L=4、受保护符号 258 字节时，4 个列累加区约占 1032 字节。若模块还承担 16 个源包的严格重排，单纯负载缓存就会额外接近 4128 字节。

因此 L 同时影响突发保护、RAM 和修复窗口；不能只为覆盖更长突发而无限增加 L。

### 7.4 CPU 优化原则

后续实现应遵守以下原则：

- 实时路径禁止 `malloc/free`，由调用者提供静态内存或初始化时一次性分配。
- 对齐后按 MCU 自然字长进行 32 位或 64 位 XOR，末尾再处理不足一个字的部分。
- 源包正常到达时走最短路径，避免无意义拷贝和全块扫描。
- 使用位图、计数器和预计算的 `row/col` 递增状态，避免每包执行除法和取模。
- 编码器支持 scatter-gather 或头部预留时，源帧尽量零拷贝；修复符号必须写入内部累加区。
- 解码器对正常源包尽量零拷贝回调；只有恢复包需要写入恢复缓冲区。
- profile 的 D、L 和 `symbol_size` 在上下文初始化后固定，减少热路径条件分支。
- 所有上下文可重入，不使用可变全局状态，以便多个流或多个无线链路并存。
- 统计计数使用饱和或明确回绕规则，不能影响数据路径。

## 8. 交织带来的窗口和时延代价

设上层输入相邻源包的时间间隔为 `T_in`，一个无线帧的空口及调度时间为 `T_tx`。若修复包在整个源块完成后发送，保守修复窗口约为：

```text
D_window ≈ D × L × T_in + L × T_tx + queue_jitter
```

更精确的数值取决于 DSP 提交节奏、RF 队列和源包/修复包的实际调度。FEC API 不需要理解音频，但调用者必须给出最大窗口或超时；否则解码器无法判断旧块何时释放。

XOR+交织的关键交换关系如下：

| 调整 | 好处 | 代价 |
| --- | --- | --- |
| 增大 D | 冗余 `1/D` 降低 | 整块跨度变长，同列再次丢包机会增加 |
| 减小 D | 修复更快 | 空口冗余增加 |
| 增大 L | 可分散更长连续突发 | RAM、块跨度和最坏等待增加 |
| 减小 L | RAM 和等待降低 | 突发保护长度降低 |

因此 XOR+交织并不天然等于低时延：它的**计算时延很低**，但为了交织可能产生较长的**等待时延**。

## 9. XOR+交织与 RS 的公平比较

### 9.1 XOR+交织占优的情况

- MCU 算力和功耗非常敏感。
- 丢包以长度有界的连续突发为主。
- 可以容纳 `D×L` 源包的修复窗口。
- 目标冗余为 12.5%、20%、25% 等 `1/D` 档位。
- 希望代码小、测试空间有限、最坏执行时间容易证明。

### 9.2 RS 占优的情况

- 丢包较分散，同一交织列出现两个以上丢包的概率不可忽略。
- 允许的修复窗口较短，无法通过增大 L 分散突发。
- 要求“块内任意 r 个丢包均可恢复”，而不是依赖丢包位置。
- 目标 MCU 有足够算力、查表空间或 SIMD/硬件支持。

### 9.3 同开销示意

- XOR 交织 D=4、L=4：16 个源包 + 4 个修复包，25% 开销；理想情况下可恢复不超过 4 个连续丢包，但两个同列丢包失败。
- RS(20,16)：16 个源包 + 4 个修复包，同为 25% 开销；可恢复 20 个传输包中的任意 4 个丢包，但 GF 运算明显更多。
- 四个独立 XOR(5,4) 组不交织：同为 25% 开销和 16 个源包，只能保证每个局部组一个丢包；合理交织这些组后才得到对连续突发更好的分布。

在相同冗余下，XOR+交织节省的是计算量，牺牲的是丢包位置无关性；RS 提供更强的确定性，牺牲的是 cycles/byte、代码量和验证复杂度。

## 10. 推荐 profiles

首版协议应预留多个 profile，但先实现并验证 XOR profiles，RS profiles 可在同一接口下后续加入。

| Profile | 参数 | 冗余 | 理想连续突发能力 | 核心特点 |
| --- | --- | ---: | ---: | --- |
| `FEC_NONE` | 无 | 0% | 0 | 吞吐和时延基线 |
| `FEC_XOR_I_4_4` | D=4, L=4 | 25% | 4 | **首轮默认评估** |
| `FEC_XOR_I_5_4` | D=5, L=4 | 20% | 4 | 降低空口冗余，窗口更长 |
| `FEC_XOR_I_4_8` | D=4, L=8 | 25% | 8 | 更强突发分散，RAM/窗口翻倍 |
| `FEC_RS_8_6` | n=8, k=6 | 33.3% | 任意 2 包 | 短块增强档 |
| `FEC_RS_10_8` | n=10, k=8 | 25% | 任意 2 包 | 与 25% XOR 档对比 |

“理想连续突发能力”要求实际发送顺序满足第 6.4 节约束，并且不存在额外重排或多段相关丢包。它是测试目标，不是脱离空口调度的无条件承诺。

## 11. FEC 帧格式建议

FEC 不采用 RFC 6015 的 RTP 头，但可复用其 D×L 一维交织数学模型。自定义空口协议至少需要以下语义：

| 字段 | 作用 |
| --- | --- |
| `version` | 协议和矩阵规则版本 |
| `algorithm` / `fec_profile` | 唯一确定 NONE、XOR、RS 及参数 |
| `stream_id` | 区分多个独立编码上下文 |
| `session_epoch` | 区分重启前后的同编号块 |
| `block_id` | 标识一个 D×L 源块或 RS 源块 |
| `frame_type` | SOURCE 或 REPAIR |
| `source_seq` | 原始上层包顺序号；修复包可携带块基准序号 |
| `row` / `col` | XOR 交织位置；可由块内索引推导以节省头部 |
| `symbol_size` | 受保护符号长度；固定 profile 时可省略 |
| `payload_length` | 当前帧有效负载长度 |
| `header_integrity` | 防止 profile、块号和索引错误污染状态机 |

首版建议用 `fec_profile` 映射固定 D、L 和 `symbol_size`，而不是每个包携带自由参数。profile 只能在新块边界切换；控制面必须能重复通告当前 profile。

FEC 外层头只负责路由到正确解码状态，不能依赖它恢复丢失源包的业务内容。原始长度等需要恢复的信息必须放进受保护符号内。

## 12. DSP 调用接口语义

本节只定义行为，不定义 C 函数签名。

### 12.1 编码端

初始化输入：

- profile、最大上层包长度、stream/session 标识；
- 调用者提供的工作内存和输出缓冲；
- 输出回调或 pull 队列；
- 块超时/flush 策略。

每次 DSP 提交一个原始包后：

- 编码器立即产生一个系统型 SOURCE 帧；
- 同时把受保护符号 XOR 到对应列累加器；
- 在一个 D×L 源块完成时产生 L 个 REPAIR 帧；
- 一次 push 可能产生 1 个或 1+L 个输出，接口必须允许调用者逐个 drain，不能假设永远一进一出。

流结束、DSP discontinuity 或 profile 切换时：

- 调用者必须显式 flush/reset；
- 不完整块可以按配置丢弃，或使用单独的短块 profile；
- 禁止用隐式补零伪造不存在的 DSP 包，除非协议明确发送有效包位图。

### 12.2 解码端

每次提交一个已通过底层完整性检查的 FEC 帧后，解码器可能：

- 立即输出 1 个正常 SOURCE 中的原始 DSP 包；
- 输出 0 个包，只更新修复状态；
- 在收到 REPAIR 后恢复并输出 1 个此前缺失的 DSP 包；
- 因重复、过期、profile 不匹配或格式错误拒绝输入。

一次调用可能触发多个旧块完成，因此推荐 callback 或 pull 模式，不把返回值设计成单一包指针。

调用者应周期性提供当前时间或显式推进过期处理。解码器释放旧块时返回每个缺失 `source_seq` 的不可恢复状态，供 DSP 或上层决定后续行为。

### 12.3 缓冲区所有权

- 初始化时明确所有工作区大小，热路径不分配堆内存。
- 输入缓冲在调用返回后是否仍需有效必须明确；首版建议编码器同步吸收数据，不长期持有 DSP 指针。
- 零拷贝 SOURCE 输出需要调用者预留 FEC 头空间或支持 scatter-gather。
- 恢复包由解码器工作区生成，回调返回后是否可复用必须在接口契约中固定。
- 不允许让 DSP 与 FEC 同时修改同一缓冲区。

## 13. 状态机和异常处理

编码器至少包含：`IDLE`、`COLLECTING`、`REPAIR_READY`、`FLUSHING`、`ERROR`。

解码器每个活动块至少记录：

- profile、block_id、session_epoch；
- 每列源包位图和修复包标志；
- XOR 累加器和恢复结果缓冲；
- 首包到达时间、过期时间；
- 已输出 source_seq 位图，避免重复回调。

必须覆盖以下异常：

- 包重复、乱序、跨块迟到；
- 块号和序号回绕；
- 发送端重启但 block_id 重复；
- profile 在块中途变化；
- 长度超限、行列索引非法、头校验失败；
- 活动块数量超过上限；
- flush 时块不完整；
- 修复包先于源包到达；
- 已输出正常源包后又收到重复恢复结果。

活动块表必须有固定上限。达到上限时按明确的最旧块/已过期块策略淘汰并计数，不能退化为动态扩容。

## 14. 正确性、完整性和安全边界

- XOR 解码假设所有参与运算的符号正确；每个 RF 帧必须先通过 CRC 或等价完整性检查。
- FEC 头中的 profile、块号、行列号同样必须被完整性保护。
- 恢复出的受保护符号必须再次验证 `source_integrity` 和 `original_length` 后才输出。
- 恢复条件不足时返回 `UNRECOVERABLE`，禁止输出猜测内容。
- 如果使用加密，源帧和修复帧必须采用一致的完整性与认证策略；不能只保护源包而允许修复包被篡改。
- FEC 模块只处理可信长度范围，所有乘法、偏移和缓冲区计算必须进行整数溢出检查。

## 15. 验证与性能测试计划

### 15.1 XOR 算法正确性

1. 固定 D、L 和变长包测试向量，发送端和接收端逐字节一致。
2. 对每一列穷举单个源包擦除，必须全部恢复。
3. 穷举修复包丢失、源包+修复包丢失、同列双源包丢失，结果必须与规则一致。
4. 对每个起始位置注入长度 1..L 的连续空口丢包，验证实际发送顺序下全部恢复。
5. 注入长度 L+1 及更长突发，确认失败被检测而不是静默错误。
6. 注入多个分离突发和周期性同列丢包，识别交织方案的弱点。
7. 覆盖变长包、最大包、零长度包、补零、乱序、重复、回绕和重启。

### 15.2 嵌入式性能指标

必须在目标 MCU 和量产编译选项下测量：

- 编码 cycles/byte、平均耗时、P99 和最大耗时；
- 正常源包解封装耗时和单包恢复耗时；
- 块完成时一次产生 L 个修复包的峰值耗时；
- 工作区、栈、代码段、只读表和输出队列占用；
- 对齐与非对齐负载、不同 `symbol_size` 的性能；
- 中断、DMA 和其他实时任务并发时的最坏执行时间；
- 交织窗口、实际 RF 发送窗口和活动解码块峰值。

性能报告应同时给出 XOR_I_4_4 和 RS_10_8 的结果。只比较平均吞吐没有意义，嵌入式实时路径必须关注最坏执行时间和峰值 RAM。

### 15.3 丢包轨迹

收集每个接收设备的：

- 原始包序号和到达时间；
- 单包丢失率；
- 连续丢包长度 CDF；
- 间隔为 L 的同列双丢包概率；
- 源包与修复包分别的丢失情况；
- FEC 后不可恢复包数和恢复完成时间。

使用真实轨迹离线回放 XOR_I_4_4、XOR_I_5_4、XOR_I_4_8、RS_8_6 和 RS_10_8，才能公平选择最终 profile。

## 16. 实施阶段与决策门

### 阶段 A：接口和 XOR+交织原型

- 固化不透明包输入/输出接口、缓冲区所有权和错误码。
- 实现 NONE 与 XOR 一维交织 profiles。
- 先完成 PC 离线故障注入，再进行目标 MCU 性能测试。
- 与 RF 同事确认源帧/修复帧实际发送顺序不会破坏列间隔。

### 阶段 B：参数定型

- 用真实轨迹选择 D、L 和 `symbol_size`。
- 确认最大修复窗口、活动块数和 RAM 上限。
- 固化帧头位宽、回绕规则、profile 切换和 flush 行为。

### 阶段 C：RS 对比

满足任一条件时实现 RS 增强 profile：

- 同列双丢包是 XOR 失败的主要原因；
- 为覆盖目标突发必须把 L 增大到 RAM 或修复窗口不可接受；
- 要求在短块内确定性恢复任意两个以上丢包；
- 目标 MCU 基准表明 RS 的最坏执行时间和功耗可接受。

### 阶段 D：最终选型

- 如果 XOR+交织达到恢复率、窗口和 RAM 指标，则它作为默认 profile，RS 可不进入低配产品。
- 如果 XOR+交织恢复率不足但 RS 达标，则 RS 作为默认或高可靠 profile。
- 如果不同工作环境差异明显，保留 XOR 与 RS 两类 profile，由控制面在块边界切换；DSP 接口保持不变。

## 17. 最终建议

1. 把模块定位为通用、媒体无关的包级 FEC 库，DSP 包作为不透明字节串处理。
2. 首版优先采用一维 XOR+交织，以 D=4、L=4、25% 冗余作为评估起点。
3. FEC 协议和接口从第一天保留 `fec_profile`，避免将 XOR 参数写死在 DSP 调用层。
4. 利用列累加器实现流式编码/解码，正常源包立即输出，核心工作区控制在约 `L×symbol_size`。
5. 明确交织的代价是更长修复窗口；RF 实际发送顺序必须保持列间隔，否则突发保护结论不成立。
6. RS(8,6) 和 RS(10,8) 作为增强对照，用真实丢包轨迹、cycles/byte、峰值 RAM 和最大修复窗口决定是否纳入产品。

## 19. 实现状态

首版实现位于 `FEC/code`，对外使用纯 C ABI，内部使用 C++11。当前已经实现：

- NONE、全部规划的一维 XOR 交织 profiles；
- 系统型 RS(8,6) 和 RS(10,8) 增强 profiles；
- 手工序列化线协议、头部/负载 CRC32 和恢复符号完整性检查；
- 乱序、重复、repair-first、活动块淘汰、超时和流结束 flush；
- 解码统计、多设备最差链路聚合、快速增强/缓慢降级控制器；
- 纯 C 调用方编译测试、XOR 突发故障注入和 RS 双擦除组合测试。

当前主机测试不能替代量产 MCU 测试。进入平台集成后仍需测量 cycles/byte、最大单次执行时间、栈/RAM 峰值、RF 队列的 `1+L` 输出峰值和真实丢包轨迹。当前 create 阶段会一次性使用堆分配；完全无堆平台需要增加 caller-provided workspace/in-place API。
